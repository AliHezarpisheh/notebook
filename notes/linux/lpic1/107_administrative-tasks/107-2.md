# Automate System Administration Tasks by Scheduling Jobs

Ok, let's set a random(but not quite random) convention. I would set my backups at 2:59.

## Cron

### Crontab

A cron job is a time-based scheduler in unix-like operating systems which is mainly for
automating tasks.

We use `cron`(it can have different names in different distros) package to manage our
cron jobs.

```bash
ali> crontab -l
no crontab for ali
ali> crontab -e
no crontab for ali - using an empty one
crontab: installing new crontab
ali> crontab -l
# Edit this file to introduce tasks to be run by cron.
#
# Each task to run has to be defined through a single line
# indicating with different fields when the task will be run
# and what command to run for the task
#
# To define the time you can provide concrete values for
# minute (m), hour (h), day of month (dom), month (mon),
# and day of week (dow) or use '*' in these fields (for 'any').
#
# Notice that tasks will be started based on the cron's system
# daemon's notion of time and timezones.
#
# Output of the crontab jobs (including errors) is sent through
# email to the user the crontab file belongs to (unless redirected).
#
# For example, you can run a backup of all your user accounts
# at 5 a.m every week with:
# 0 5 * * 1 tar -zcf /var/backups/home.tgz /home/
#
# For more information see the manual pages of crontab(5) and cron(8)
#
# m h  dom mon dow   command
16 15 3 feb * echo "a" > /tmp/a.txt
```

`cron` use a temporary file for signing up the cron tasks. Each line introduce a cron
job which should be in the below format:

```txt
m h dom mon dow command
```

So by specifying `5 * 1 jan * /root/backup.sh`, you are basically telling you want to
run /root/backup.sh in every minute five of every hour in January 1st of each year.

Let's look at some special characters:

- `*` means whatever.
- `,` you can give multiple options or numbers.
- `/` can slice the time. \*/5 means every 5 minutes(certainly in the minute field).
- `-` specify a range of values. mon-fri means monday to friday.
- `@daily` for running the command daily.
- `@reboot` for running after reboot.

> 🤯 Fun use case! If the root owns a crontab, she can put a `-` at front of the line,
> telling syslog to not store any logs for this crontab.

### User-Specific Crons

cron is user-based and by saying it is user-based I mean that every user has its own
cron jobs. The files will be saved at `/var/spool/cron/tabs/` or `/var/spool/crontabs/`(
which you should not edit! Just use `crontab -e`.)

```bash
root> cd /var/spool/cron/crontabs/
root> ls
ali
```

### System-Wide Crons

There is a file under `/etc/crontab` path, which is used by the system for defining
system-wide cron jobs. There is just another field named user in the crontab format.

```txt
m h dom mon dow user  command
```

> Favor system crontabs instead of root crontabs.

### System Hourly, Daily, Weekly, and Monthly Crons

There is a `/etc/cron.d/` directory which has some files with the same format of crontab
files. Also there are `/etc/cron.hourly/`, `/etc/cron.daily/`, `/etc/cron.weekly/`, and
`/etc/cron.monthly/` which contains scripts, which cron runs them based on their
schedules. So basically just copy past your script in the place you want!

## at

There is an interesting tool called at, which schedule commands and use `sh` to execute
it, but just once. There are related commands to it such as `atq` and `atrm` which I
believe you can guess what they will do:)! `atq` will list the user pending jobs and
`atrm` will delete one.

```bash
at now + 90minutes
warning: commands will be executed using /bin/sh
at Tue Feb  3 20:03:00 2026
at> notify-send "I think you should rest"
at>
at> <EOT>
job 16 at Tue Feb  3 20:03:00 2026
ali> atq
16 Tue Feb  3 20:03:00 2026 a ali
ali> atrm 16
```

### Whitelisting or Blacklisting Users for at and cron

You can create these files and put user names there to blacklist or whitelist them. The
`.allow` files are for whitelisting and `.deny` are for blacklisting.

```txt
/etc/cron.allow
/etc/cron.deny
/etc/at.allow
/etc/at.deny
```

## How Do systemd and systemd-run Are Replacing at and cron?

Systemd is able to work because of units. We had multiple unit types, one of them is
`timer`. This is the replacement of cron jobs. You should create a `.timer` file in the
paths that systemd saves the units, and create a corresponding `.service` file with the
same name of the timer unit, and the timer one will run the service with the given
options.

We have two types of timer units.

### Real-Time Timers

There is a `OnCalendar` parameter in the unit file, with below format:

```txt
OnCalendar=DayOfWeek Year-Month-Day Hour:Minutes:Seconds  # DayOfWeek is optional
```

You can use `*`, `/`, and `,` like the crontab format, but use `..` instead of `-`.

```bash
ali> cat apt-daily.timer
[Unit]
Description=Daily apt download activities

[Timer]
OnCalendar=*-*-* 6,18:00
RandomizedDelaySec=12h
Persistent=true

[Install]
WantedBy=timers.target

ali> cat apt-daily.service
[Unit]
Description=Daily apt download activities
Documentation=man:apt(8)
ConditionACPower=true
After=network.target network-online.target systemd-networkd.service ...

[Service]
Type=oneshot
ExecStartPre=-/usr/lib/apt/apt-helper wait-online
ExecStart=/usr/lib/apt/apt.systemd.daily update
```

Also, there are shortcuts instead of the crontab formats:

| Shortcut | When It Runs                      |
| -------- | --------------------------------- |
| hourly   | beginning of each hour            |
| daily    | once a day at midnight            |
| weekly   | midnight on Monday                |
| monthly  | midnight on the 1st of each month |
| yearly   | midnight on the 1st of January    |

### Monotonic Timers

These timers are activated after a certain time of an event. These options are available
for them:

| Config            | Meaning                                                                                                                                                                           |
| ----------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| OnActiveSec       | Time after the unit itself is activated.                                                                                                                                          |
| OnBootSec         | Time after the system boot.                                                                                                                                                       |
| OnStartupSec      | Time after the service manager is started. For system services, this is almost equal to OnBootSec. Use this for user services where the service manager is started at user login. |
| OnUnitActiveSec   | Time after the corresponding service was last activated.                                                                                                                          |
| OnUnitInactiveSec | Time after the corresponding service was last deactivated.                                                                                                                        |

You can use any of seconds, minutes, hours, days, weeks, month, and years in front of
them.

```txt
[Timer]
OnUnitActiveSec=5minutes 20seconds
```

Please note that after creating the services, you should do:

```bash
systemctl daemon-reload
systemctl enable hello.timer
systemctl start hello.timer
```

Just like services.

Use the commands for observing the timers:

```bash
sudo systemctl list-timers --all
...

sudo systemctl list-timers
```

> For checking the output of timers, use journalctl.

### systemd-run

Using `systemd-run` command, you can run a transient service or scope and run specific
commands on it.

```bash
systemd-run --on-active="2hours" --unit="helloworld.service"

Copy
sudo systemd-run --on-active="2hours" /usr/local/bin/helloworld.sh --language=en_US
```
