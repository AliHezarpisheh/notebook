# Oauth 2.0 Dynamic Client Registration Protocol

This specification defines mechanism for dynamically registering Oauth 2.0 clients with
authorization servers. This is the foundation on how clients get onboarded
programmatically.

## What Problem Does it Solves?

Traditionally, a client should be registered in a developer portal or somehow, someone
should manually register those clients. This is fine and cool, until we get to a point
where the client software should communicate with hundreds or thousands of different
authorization servers, or the the authorization server is not specified at the compile
time and the client software doesn't have any idea which endpoints and domains it would
interact with.

[RFC-7591](https://datatracker.ietf.org/doc/html/rfc7591) introduces a
machine-to-machine registration protocol, so a standardized client registration endpoint
is present in the authorization server, which the client can **POST** its desired
metadata to that well-known endpoint and get a `client_id` back. No human is involved
here.

## Actors

There are four type of actors here:

- **Client Software**: The codebase.
- **Client Instance**: The running process of thw software.
- **Client Developer**: The org or person that builds the software.
- **Client Registration Endpoint**: The AS's HTTP endpoint that accepts registration
  requests.

## Flow

It involves simple request/response flow:

- *optional*: Client is handed an initial access token out-of-band.
- *optional*: Client is handed a **software statement**.
- Client `POST` a JSON document describing itself tot he client registration endpoint.
- AS responds with a `client_id`, optionally a `client_secret`, and the full set of
  registered metadata.

> 🖊 RFC-7591 only standardized the registration exchange itself, not the trust
> bootstrapping around it.

### The Registration Request

```http
POST /register HTTP/1.1
Content-Type: application/json
Host: as.example.com

{
  "redirect_uris": ["https://app.example.org/callback"],
  "client_name": "My Example Client",
  "token_endpoint_auth_method": "client_secret_basic",
  "grant_types": ["authorization_code", "refresh_token"],
  "response_types": ["code"],
  "scope": "read write"
}
```

If the AS requires authorization to register(protected registration, as opposed to open
registration), you include the initial access token as the Bearer token in the
`Authorization` header.

| Field                                                            | Purpose                                                                                                                                                                                                                  |
| ---------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `redirect_uris`                                                  | Array of allowed redirect URIs. **Mandatory** to implement if the AS supports redirect-based flows — this is the anchor of open-redirect protection.                                                                     |
| `token_endpoint_auth_method`                                     | How the client authenticates at the token endpoint: `none` (public client), `client_secret_post`, or `client_secret_basic` (the default if omitted). Extensible via IANA registry or arbitrary absolute URIs.            |
| `grant_types`                                                    | Which OAuth grants the client will use (`authorization_code`, `implicit`, `password`, `client_credentials`, `refresh_token`, JWT-bearer, SAML2-bearer). Defaults to `authorization_code` alone if omitted.               |
| `response_types`                                                 | Which authorization endpoint response types it'll use (`code`, `token`). Defaults to `code`.                                                                                                                             |
| `client_name`, `client_uri`, `logo_uri`, `tos_uri`, `policy_uri` | Human-facing presentation metadata shown to the resource owner on the consent screen.                                                                                                                                    |
| `scope`                                                          | Space-separated default scope list the client may request.                                                                                                                                                               |
| `contacts`                                                       | Array of contact addresses (usually emails) for whoever's responsible for the client.                                                                                                                                    |
| `jwks_uri` / `jwks`                                              | The client's public keys — used for things like private_key_jwt token endpoint auth or signed request objects. These two are mutually exclusive in a single request.                                                     |
| `software_id` / `software_version`                               | An identifier that's stable across *all instances and versions* of a piece of client software (unlike `client_id`, which is per-instance). Useful for the AS to correlate "oh, this is another install of the same app." |

Some considerations:

- **grant_types** and **response_types** are correlated, not independence. For example,
  if you request the `authorization_code` grant, you'd also better request the `code`
  response type. **If the grant_types and response_types make a conflict, server should
  response with `invalid_client_metadata` error**. Section 2.1 gives the full
  correlation table.
- Human-readable fields can carry BCP 47 language tags append with `#`; e.g.
  `client_name#ja-Jpan-JP`.

### The Response

A `HTTP 201 Created` with JSON body:

```json
{
  "client_id": "s6BhdRkqt3",
  "client_secret": "cf136dc3c1fc93f31185e5885805d",
  "client_id_issued_at": 1752192000,
  "client_secret_expires_at": 0,
  "redirect_uris": ["https://app.example.org/callback"],
  "grant_types": ["authorization_code", "refresh_token"],
  "token_endpoint_auth_method": "client_secret_basic"
}
```

Some considerations:

- `client_secret_expires_at`: 0 means never expires.
- The AS is required to echo back all registered metadata.

Failure should be responded with `HTTP 400 Bad Request`, with codes including:
`invalid_redirect_uri`, `invalid_client_metadata`, `invalid_software_statement`,
`unapproved_software_statement`.

## Software Statement

When a client registers itself, it fills out a form and say things that I'm X, my logo
is Y, and so on. Nobody is stopping a random dude on the internet that is saying "I'm
the official PayPal app".

That's what self-asserted means, the clients is asserting facts about itself with zero
proof behind them. This is like walking up to a bouncer and claiming "I'm X".

On the other hand, a `software statement` is like showing an actual passport, a document
that an authority, created, stamped, signed, vouching "This person is who they say they
are". The authority's signature is what makes the statement **trust worthy**.

In OAuth terms, the authority is the software publisher, the passport is a signed JWT,
and the signature is a cryptographic signature (JWS) using the publisher's private key.

So the flow is:

- Before any registration happens, the software publisher (say, "Notion") creates a JWT.
  Inside of it they put claims about themselves, like: `"client_name": "Acme Notes"`,
  `"client_uri": "https://acme.com"`, `"software_id": "acme-notes-v2"`.
- Notions signs that JWT with their own private key. The signed JWT is now the
  **software statement**.
- This pre-signed software statement (basically the JWT), is baked to the registration
  request.
- The authorization server reacts by verifying the JWT by the public key of the
  publisher.
- Now the AS should override any conflicting value sent as plain JSON.

> 💡 However the authorization server obtain and trusts the public key is outside spec's
> scope. That's a separate trust establishment problem.

This is a separate trust mechanisms compared to **initial access token**:

- **Software Statement**: Is the metadata about client trustworthy?
- **Initial Access Token**: Is this caller even allowed to hit the registration
  endpoint?

## Security Considerations

- Use **TLS >= 1.2**.
- Redirect URI validation is the primary attack surface. The spec constraint valid
  Redirect URIs to three shapes: HTTPS remote sites, HTTP for local apps, or private URI
  schemes for native apps(exampleapp://oauth_redirect). This exists to prevent
  **open-redirector** attacks when an attacker registers a client with a redirect URI
  they control to intercept auth codes.
- All self-asserted metadata should be treated as untrustworthy by default, unless it
  arrives in a signed software statement.
- Open registration is heavily discouraged.
- Client software should not chose its `client_id`.
