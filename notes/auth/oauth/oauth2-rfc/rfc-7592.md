# Oauth 2.0 Dynamic Client Registration Management Protocol

This specification define methods for management of Oauth 2.0 dynamic client
registrations for use cases in which the properties of a registered client may need to
be changed during the lifetime of the client

This spec is completely build on its previous RFC.

## The Gap RFC-7591 Left Open

In the previous RFC, no mechanism were introduced which by using them, we could:

- Check client's metadata again.
- Update the client's metadata.
- Delete a registered client.

[RFC-7592](https://datatracker.ietf.org/doc/html/rfc7592) fills the gap. It's worth
noting that it is published as an experimental RFC, not a Standard Track Document,
unlike 7591.

## Concepts

RFC-7592 introduces two new concepts on previous RFC:

- **Client Configuration Endpoint**: A per-client URL, where the client can be read,
  updated, or deleted.
- **Registration Access Token**: A bearer token, scoped to exactly one registered
  client, that authenticates calls to the client configuration endpoint.

## Flow

The RFC-7591 finishes at the `D` step, but the new rfc extends it:

```txt
(C) Client Registration Request  ─────────>  Registration Endpoint
(D) Client Information Response  <─────────  (client_id, client_secret,
                                               registration_access_token,
                                               registration_client_uri)

(E) Read or Update Request       ─────────>  Configuration Endpoint
(F) Client Information Response  <─────────  (current config, possibly
                                               rotated credentials)

(G) Delete Request                ─────────>  Configuration Endpoint
(H) Delete Confirmation            <─────────  (204 No Content)
```

Very important note, that the client information response is now extended and we have a
`registration_client_uri` and `registration_access_token` params.

## Operations

All three call the same client configuration endpoints, but with different methods.

### GET

```http
GET /register/s6BhdRkqt3 HTTP/1.1
Host: server.example.com
Authorization: Bearer reg-23410913-abewfq.123483
```

Returns `200 OK` with the current registration.

> ⚠ The `client_secret` and the `registration_access_token` may differ from what was
> originally issued. So, reading your config can simply result in a credential rotation.

### PUT

```http
PUT /register/s6BhdRkqt3 HTTP/1.1
Authorization: Bearer reg-23410913-abewfq.123483

{
  "client_id": "s6BhdRkqt3",
  "client_secret": "cf136dc3c1fc93f31185e5885805d",
  "redirect_uris": ["https://client.example.org/callback", "https://client.example.org/alt"],
  "grant_types": ["authorization_code", "refresh_token"],
  "client_name": "My New Example"
}
```

Few considerations:

- This is a PUT method, so it is a full replace and you should resend every metadata
  field you want to keep.
- You should echo back your client_id and client_secret, and you can not replace them.
- You must not include `registration_access_token`, `registration_client_uri`,
  `client_secret_expires_at`, or `client_id_issued_at` in the request body, server
  controls them.

### DELETE

```http
DELETE /register/s6BhdRkqt3 HTTP/1.1
Authorization: Bearer reg-23410913-abewfq.123483
```

Success is `204 No Content`. This meant to be hard-kill.

### Error Semantics

Consistent status codes regardless of the operations.

| Situation                                                    | Status                                                |
| ------------------------------------------------------------ | ----------------------------------------------------- |
| Registration access token invalid/expired                    | per RFC 6750 bearer token error (typically `401`)     |
| Client no longer exists on the server                        | `401 Unauthorized` (token should also be revoked)     |
| Client exists but lacks permission for this action           | `403 Forbidden`                                       |
| Method not supported by this server (e.g. no DELETE support) | `405 Method Not Allowed`                              |
| Invalid metadata on PUT with no substitutable default        | `invalid_client_metadata` per RFC 7591's error format |

## Credentials

There are three distinctive credentials that plays their part in these two RFCs.

| Credential                | Issued at                        | Used at                     | Scope                                                                     |
| ------------------------- | -------------------------------- | --------------------------- | ------------------------------------------------------------------------- |
| Initial access token      | out-of-band, before registration | registration endpoint only  | may be shared across multiple client instances from the same developer    |
| Registration access token | registration response (7592)     | configuration endpoint only | bound to one specific `client_id`; must never be shared between instances |
| Client secret             | registration response            | token endpoint only         | authenticates the client itself when requesting tokens                    |

> ⚠ Never ever share the registration access token among instances. Each instance should
> have its own token.

It's a good practice to rotate the access token on every read and update requests.
